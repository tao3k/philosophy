* 问题
:PROPERTIES:
:CUSTOM_ID: philosophy.reflection.30.190-when-services-face-agents-cn
:END:
当航司、餐厅、商店、日历和公共服务收到的直接请求不再来自一个操作屏幕的人，而来自替人搜索、
协商和执行的 Agent，设计标准应把谁当作对象？服务只要让 Agent 调用得快、成功率高就够了吗？
* 论证
讨论 Agent 成为直接对象，不能只问接口怎样更适合机器调用，也不能退回只看屏幕前个人的传统框架。
需要沿着一次行动同时辨认直接调用者、托付来源、受影响者、执行劳动与公共规则。
** 传统对象与适用边界
传统 GUI 设计通常假定眼前有一个人：这个人看见选项、进行操作、收到反馈，也能在出错时返回。
传统 API 设计则假定调用者是相对稳定的软件，开发者预先理解字段、错误码和业务关系。两者都有重要
积累，却都没有完整面对一种会理解自然语言、临时组合工具、代表不同委托人并与另一个 Agent 协商的
调用者。

因此，传统标准仍能回答按钮是否可达、信息是否清楚、接口是否一致，却不能单独回答 Agent 的一句
请求背后有谁、授权持续多久、受影响者是否出现、机器间达成的承诺怎样回到人，以及服务能否针对
“机器客户”悄悄改变价格和选择。
** 对象变革
直接交互对象可能已经是 Agent。它读取能力说明、比较结构化结果、调用工具、处理错误并继续下一步。
服务无需先为它绘制一套人类页面；为人准备的 APP 也可能只在异常、复核或争议时出现。

可是直接对象不是全部对象。Agent 背后有委托人，旁边有同行者和共同承担者，另一端有接电话、备餐、
改签和处理申诉的人，外面还有市场规则与公共责任。若设计只优化 Agent 的完成率，就会把这些人变成
“外部条件”，即使他们才是后果真正落下的地方。

#+NAME: agent-facing-design-objects-cn
#+EXPLANATION: Agent 是直接调用者时，设计仍需区分不同位置，不能把它们压成一个抽象 user。
| 位置 | 它拥有什么 | 它不自动拥有什么 | 标准需要看见什么 |
|------+------------+------------------+--------------------|
| Agent | 解析请求、调用能力、保留过程状态 | 委托人的全部权利与价值判断 | 身份、任务范围、权限凭据、状态与失败 |
| 委托人 | 设定目的、给予和收回一定托付 | 代表所有受影响者决定的资格 | 真实意图、边界、理解与可达的申诉 |
| 受影响者 | 对自己的时间、财产、身体和关系有声音 | 发起者界面中的默认席位 | 何时需要同意、怎样被告知、怎样拒绝 |
| 服务劳动者 | 现场知识、执行与纠错能力 | 承担代理错误的无限义务 | 工作转移、身份说明、升级与补偿 |
| 机构与公共规则 | 维护交易、平等、安全和争议处理 | 把合规等同于正当的权力 | 可审计规则、差别待遇、责任与救济 |
** 判断
当前判断是：服务可以把 Agent 当作直接交互对象，却不能把 Agent 当作唯一的设计主体。新标准应同时
约束机器可理解的能力边界与人可承担的生活后果。它不必为 Agent 模仿一套 GUI，而要让权限、代价、
副作用、可逆性、部分完成和完成证据能够被 Agent 正确处理，也能被翻译回有关的人。

因此，标准的中心不再是“页面是否容易操作”，也不能变成“协议是否容易调用”。它要回答一条行动链
怎样保持意义与责任：谁提出什么目的，Agent 以什么身份和权限行动，服务改变了什么，哪些人受到
影响，失败怎样回到可以处理它的人。

** 面向 Agent 的标准需要什么

第一，能力必须以清楚边界出现。服务应说明前提、成本、会改变的状态、可撤销期限与可能只完成一部分
的情形，而不是只给一个“成功”入口。

第二，权限不能从能力推断。Agent 知道怎样购票，不代表它被允许付款；它能访问家庭日历，不代表它
可以替所有成员改期。服务需要识别 Agent 代表谁、此次托付范围是什么、哪些权利必须由另一方给出。

第三，结果必须能回到人。机器可读回执可以很详细，人收到的说明不必复述所有调用，却要说清费用、
承诺、影响、未完成部分与下一步。若只有 Agent 能理解日志，人在争议时仍然失去位置。

第四，Agent 必须诚实表明自身。打电话订位或谈判时，对方应知道正在与代理系统交互、它代表谁以及
怎样找到有权的人。便利不能依赖伪装成人。

第五，服务不得利用“机器不会疲倦”无限增加阻碍，也不得利用 Agent 背后的数据做不可见差别定价、
排序或劝诱。人不操作页面，不等于市场权力消失。

第六，标准要容纳停止和未定。两个 Agent 很快找到一个可行解，不代表有关的人已经作出承诺。机器
之间的协调应能停在草案、暂存或待同意状态。
** 论证与辩论场景
以下场景检验“Agent 可以成为直接对象，但不能成为唯一主体”的判断。它们也说明，同一种技术结构
进入不同生活关系后，所需标准不会完全相同。

#+NAME: services-facing-agents-debate-cn
#+EXPLANATION: 场景把机器间效率与落在人身上的权利、劳动和救济放在同一判断中。
| 场景 | 支持当前判断的理由 | 反方理由 | 会改变判断的证据 |
|------+--------------------+----------+------------------|
| 航司接口直接面对旅行 Agent | 无需让人反复搜索和填表；规则可机器读取 | 航司可能按代理画像差别排序，同行者和退改风险被隐藏 | 可验证的完整价格与规则、同行者同意、可携带回执和人工争议入口 |
| 餐厅接到 AI 电话 | 可跨语言、跨时区完成预约并减少等待 | 员工需要识别代理、核验特殊需求并承担错误 | 代理表明身份、限制披露，双方收到一致内容且错误有明确承担者 |
| 两个日历 Agent 协商 | 大量时间约束可快速求交集 | 它们可能把照护、通勤和权力不对称当作普通偏好 | 受影响者能声明不可交换条件，草案不自动成为承诺 |
| 购物 Agent 与商家 Agent 议价 | 可持续比较真实总成本并执行预算 | 平台可能识别支付能力、制造个性化价格并遮蔽替代品 | 排序与价格差异可追问，利益关系可见，退出不受惩罚 |
| Agent 申请公共服务 | 可帮助语言、认知或行动受限者整理材料 | 错误代理可能扩大排除，自动拒绝难以申诉 | 决定理由能回到申请人，人工救济可达，代理使用不造成差别待遇 |

一个可能的反方观点是：既然委托人已经选择 Agent，服务只需验证凭据并正确执行，不必承担其余关系。
这个观点在低风险、私人的只读查询中可能成立；一旦行动影响共同财产、他人时间、资格和公共机会，
“只认调用者”就会把社会后果推到协议之外。标准需要按后果收敛，而不是对所有请求施加同样重量。
** 原则与治理边界
本文仍是 Reflection。它提出标准应关注多重对象的判断和候选内容，却没有把它们直接写成 Charter
Principle。若要规定 Agent 必须披露身份、哪些行动必须取得谁的同意，需另写 Principle，说明范围、
冲突权利、例外与失败方式。

Governance 负责另一类问题：谁可以修改标准，哪些证据足以准入或修订，利益冲突怎样公开，申诉和
事故怎样进入生命周期。不能因为本文讨论“标准”就把内容判断与治理权限混在一起。

* 反例
第一，有些机器间交互早已长期稳定运行，人并不需要理解每个技术步骤。若新标准要求每次都把全部
过程翻译给人，会抵消自动化价值。需要显露的是实质后果和异常，不是协议噪声。

第二，过度要求 Agent 表明委托人可能泄露隐私，也可能让匿名求助、敏感查询和受迫处境中的人更危险。
身份应与所需权限相称，而不是把实名当作普遍答案。

第三，服务无法知道调用者没有告诉它的全部关系。标准不能假装技术系统能穷尽受影响者；它只能要求
在已知后果和合理可发现关系上停下、询问或限制行动。

第四，对 Agent 施加额外限制可能保护既有平台、排斥小型或开源代理。安全与责任要求若无法公开验证、
成本过高，也会把新入口重新集中到少数公司手里。
* 暂定结论
当服务直接面对 Agent，传统意义上的“用户”裂成了多个位置。Agent 是真实的交互对象，却不是价值和
权利的最终来源；委托人是目的来源，也不是所有受影响者的主人。新的标准必须沿着行动链同时看见
机器怎样理解能力，以及后果怎样回到人、劳动和制度。

这是一种对象变化后的设计，而不是给旧 APP 加一层自动化。它允许没有 GUI 的服务，也要求没有 GUI
之后仍然存在可以理解的承诺、相称的权限、可追问的差别、明确的失败和可达的救济。
* 仍需面对的问题
还需研究多个 Agent 怎样证明自己没有重复承诺、怎样处理代理身份被冒用、怎样让公共服务既接受代理
帮助又不歧视没有代理的人，以及当模型供应商、服务平台和支付方同时参与时谁保存最小而充分的记录。

更深的问题是：当越来越多服务为 Agent 而非人优化，人是否还能直接理解市场、公共规则和可选路径；
服务劳动者能否拒绝或限制机器来电；下一代人会不会只看见个人代理给出的世界。专题需要继续从这些
未被“调用成功率”表示的地方接受修正。
