本条综合多个 Agent 工程项目中关于状态、提议、决策、授权、执行与结果回执应保持区分的
设计取向；它不声称已经提供时点工程证据。若要升格为 =ENGINEERING_EVIDENCE=，必须另行记录
repository、revision、RFC/path 与 observation date。

外部设计锚点是 Saltzer 与 Schroeder 的
[[https://web.cs.wpi.edu/~cs557/f14/papers/saltzer1975_alt.html][The Protection of Information in Computer Systems]]。其 least privilege、fail-safe defaults 与 complete mediation 说明，访问能力应受最小范围与持续检查约束。本条借用这些原则检验 Agent authority，但不把信息保护等同于全部规范授权。

* 语境

经典 protection 讨论主要防止未授权的信息访问与修改；Agent 系统进一步把模型生成的 proposal 接到可改变
金融、医疗、代码与通信状态的工具上。此时“进程拥有什么权限”仍重要，但还必须问 principal 是谁、目的
是什么、委托是否仍有效、行动的现实后果由谁复验。

Tao3k 工程综合反复遇到相同边界：检索结果不是 admitted knowledge，候选计划不是 decision，工具 schema
不是 authority，transport success 不是 outcome。它们应保持不同状态，不是为了增加层级，而是为了让每次
跨越都能独立拒绝、追溯与撤销。

权限还会随委托链传播。最小权限要求 scope 衰减，fail-safe default 要求缺少明确授权时不执行，complete
mediation 要求每个现实改变在使用时检查权限而不是只在 session 建立时检查。这些安全原则为 Agent 设计
提供强反例，但 purpose、consent、benefit-harm 与补偿仍需要更广的哲学论证。

* 解释边界

当前 Tao3k 实现只是可替换的 realization，不能反向定义永久哲学规范。least privilege 也不证明任何具体
token、capability 或 approval UI 正确；权限形式可以不同，只要能表达主体、范围、时间、目的、衰减与撤销。

安全授权与规范正当性不能坍缩。一个调用可能通过所有访问控制，却仍违背用户目的或造成不成比例伤害；
另一个调用可能有充分善意，却因没有 authority 而不得执行。本条只说明二者必须同时成立。

* 影响

进入 [[file:../30-reflections/30.60-action-requires-authority.org][Action 必须经过 Authority]]，并为行动与权限专题 Charter 提供工程反例：隐式凭据继承、过期授权、scope 放大、只在 session 建立时检查、撤销后仍执行，以及把 invocation receipt 当 outcome。

* 解释链

Saltzer/Schroeder protection principles 与 Tao3k 工程实践 → capability/authority/outcome 边界 → [[file:../30-reflections/30.60-action-requires-authority.org][对应反思]] → 可能的专题 Charter。安全原则约束权限机制；purpose、human agency 与 outcome reconciliation 是本仓库的扩展，不能反向归于原论文或当前实现。
