* Authority
:PROPERTIES:
:CUSTOM_ID: governance-authority-en
:END:

The authoring entry point is the [[file:../../justfile][Justfile]]; shell only forwards arguments to
=orgize contract workspace=. Org AST parsing, exact path indexing, linear contract composition,
CN/EN pairing, and semantic assertions are executed by =tao3k/orgize=. The workspace policy,
contract registry, and bilingual documents jointly define admission.
No implementation repository, author, or cited source independently creates Tao3k normative authority.

* Lifecycle

The principle state machine is:

#+begin_src text
draft -> proposed -> accepted -> superseded
                              \-> withdrawn
#+end_src

Every principle node declares =PRINCIPLE_ID=, =PRINCIPLE_STATUS=, =NORMATIVE_LEVEL=, =SCOPE=,
=REVISION=, =SUPERSEDES=, =SUPERSEDED_BY=, and =CHANGE_RATIONALE=. An accepted principle is not
editable prose under a permanent identity. A meaning-preserving clarification increments =REVISION=;
a change to obligations, scope, or failure boundaries creates a new principle identity or explicit
supersession chain while retaining the old node.

* Admission

| Object | Required evidence | Admission result |
|--------+-------------------+------------------|
| CN/EN document | Unique =SEMANTIC_ID=, reciprocal =COUNTERPART=, exact contract composition | Maintained pair |
| Reflection | Argument, counterexample, provisional conclusion, promotion criteria | Open inquiry |
| Principle | First-class node, lifecycle fields, counterarguments, failure modes | Proposed or accepted norm |
| Engineering Map | Stable normative requirement separated from replaceable current realization | Traceable implementation |
| Source | Source identity, historical context, interpretation status, claim scope | No automatic normative authority |

=just check= must pass Orgize closed-world topology, unique pairing, exact linear contract
composition, and contract assertions. Orgize itself maintains scale performance and admission
regressions through the ASP Rust Scenario macro.

* Change Policy

- =draft -> proposed= requires bilingual pairing, counterexamples, boundaries, and engineering consequences.
- =proposed -> accepted= requires an explicit maintainer review; tool success is not acceptance.
- Meaning-preserving clarification increments =REVISION= and records its rationale.
- Normative meaning changes never silently overwrite an accepted principle; use =SUPERSEDES= and =SUPERSEDED_BY=.
- =withdrawn= ends the claim while retaining historical identity and evidence.

* Failure Handling

Topology escape, incorrect contract composition, non-reciprocal counterpart, a third document with the
same semantic identity, failed contract assertions, or missing interpretation metadata rejects admission.
Automation must not fill in content merely to pass; the receipt identifies the first actionable boundary.

* Review and Challenge

Any accepted principle may return to Reflection because of a new counterexample, observed engineering
failure, new scientific evidence, or value conflict. A challenge record distinguishes:

| Kind | Question |
|------+----------|
| Challenge | Which normative claim is challenged? |
| Counterexample | Which explicit case limits or defeats it? |
| Observed failure | Which real outcome diverged from expectation? |
| Revision proposal | Retain, clarify, supersede, or withdraw? |

The loop is =Charter -> Engineering -> observed counterexample -> Reflection -> revised / retained /
superseded Charter=. The repository therefore follows its own “know → act → reconcile → new knowledge” rule.
